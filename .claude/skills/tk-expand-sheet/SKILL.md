# TK 扩组导入表

投手说「给我某个账户明天最新的扩组表格」时走这套流程，产出一张他能直接导入自动化软件的
`.xlsx`。

## 这个 skill 存在的理由

客户端有「一键扩组」按钮，投手不带 agent 时就用它。但客户端只能按死规则跑，**它读不到品库**，
必然会偏：品库删掉的品它还在扩，命名认不出的品它会漏。

所以分工是——**客户端保证大致不漏不多，agent 每次被叫来时做一次精确对齐。**
不要试图把客户端做到零偏差，那不是它的职责；也不要因为「客户端已经有这个功能」就跳过这套流程。

## 最重要的一条：遍历品库，不要扫账户

这是整个 skill 的地基，做反了会**静默漏扩**，而且投手看不出来。

```
❌ 错：扫账户里的系列 → 逐条判该怎么办 → 凑出名单
✅ 对：遍历品库每一行 → 问「这个品明天有没有组在跑」 → 生成动作
```

为什么：`packages/core/src/expand-classify.ts` 把**已关停的系列判 `excluded`**，直接出局。
站在「逐条系列判」的视角这没错（系列停了，对它没动作可做），但站在「这个品明天该不该有组在跑」
的视角就是漏扩——品还在品库里，它的系列全关停了，**恰恰说明明天得给它开一条新的**。

实测：账户「余杭茵未-1PHH」54 条系列里 53 条已关停。按扫账户的做法，这个账户只有 1 个品
能进名单，其余全部静默消失。这就是投手说的「关闭后的系列不会被判需重扩，是现在漏扩的最大原因」。

按品库遍历之后，**品库有几行、输出就有几行**，漏扩在结构上不可能发生。

## 第 0 步：前置自检（跳过会静默出错）

**1. 确认 MCP 支持 `verdict="stopped"`。**

```
list_campaigns(accountId=<任一账户>, verdict="stopped")
```

报参数错误就是装的 MCP 是旧版——**立刻停下来告诉投手，不要继续**。没有这个参数就拿不到关停
系列，整套流程会退化成「扫账户」，漏掉的正是最该重扩的那批，而且输出看起来完全正常。

> 这个参数从 1.4.108 起在 master 上（PR #147），装的 bundle 是从 master 构建的就有。
> 之所以仍然保留这一步自检：MCP 跑的是**安装目录里的** `resources/mcp/mcp-server.cjs`，
> 它跟仓库代码是两回事——build 完没覆盖安装版，重启也还是旧代码。见 `mcp-runs-from-installed-bundle`。

**2. 确认品库表存在。**

```bash
python .claude/skills/tk-expand-sheet/scripts/feishu_read.py --list-tables
```

品库是**逐账户一张表**，一个账户一个品库，表名对应账户名。找不到对应账户的品库表就停下来问投手
——**不要拿源代码库「爆款整理（1.20）」当品库用**，那是两个东西（见下）。

## 流程

### 1. 定账户

`list_accounts` 拿 accountId。投手报的是账户名，别猜 ID。
账户连接状态是 `failed` / 同步 `stale` 时先说出来——快照过期意味着判定依据是旧的。

### 2. 读品库

```bash
python .claude/skills/tk-expand-sheet/scripts/feishu_read.py --table <品库表ID> \
  --fields 品名 编码 年龄 性别 url
```

品库的行数就是最终名单的行数，记下来，第 7 步对账要用。

### 3. 拉账户现状（三份都要，缺一份就会漏）

```
list_campaigns(accountId, verdict="all")      # 在投的，带判定
list_campaigns(accountId, verdict="stopped")  # 已关停的 ← 漏扩就漏在这份
list_ad_groups(accountId)                     # 找源生组用
```

判某个品「现在还在不在跑」必须合起来看。只看第一份会把整个品当成不存在。

### 4. 逐品判定

对品库的**每一行**（按编码），在账户里找它的系列，取**最新的那条**（历次重扩链的链尾）：

| 情况 | 判定 | 系列名怎么写 |
|---|---|---|
| 累计单转 ≥ 12 | **需重扩** | 新系列名 |
| 累计零转化 且 无在投组 | **需重扩** | 新系列名 |
| 观察中（花过钱但零转化） | **需重扩** | 新系列名 |
| 最新的系列已关停 | **需重扩** | 新系列名 |
| **账户里找不到这个编码** | **新建** | 新系列名 |
| 单转达标（< 12） | **可扩组** | **原系列名，逐字照抄** |
| 建好还没投（一分钱没花） | 可扩组 | 原系列名 |

「重扩」和「新建」在导入表里长得一样（都是新系列名，导入时自动开新系列），**但汇报时要分开报**：
新建的品从来没跑过，没有任何历史数据可参考，投手需要知道哪些是全新的。

规矩：
- 两条重扩判据不会同时出现，**命中即重扩**
- **判不进「可扩」的一律落「需重扩」，不允许「跳过」这个结果**。这样只会多扩、不会漏扩——多扩
  的那行投手在表里看得见，漏扩的那个品是静默消失的
- 「当天」= 自然日今天，账户时区
- 一个品有多条系列时**只判最新的那条**，旧系列不进名单（否则一个品会同时出现在两份名单里）

### 5. 生成导入表

**系列名是控制流，不是标签。** 导入软件按系列名是否重名自动分流：

```
系列名和账户里现有的一致  → 组并进那条原系列   （= 可扩组）
系列名在账户里不存在      → 自动开一条新系列   （= 需重扩）
```

所以**不需要在表里用字段标「可扩/重扩」**，判定结果就体现在你写的系列名上。

**命名规则：用投放时间规避重名。**

```
可扩      系列名 = 账户里的原系列名（逐字照抄，绝不加后缀——加了就变成新开一条）
重扩/新建 系列名 = {品库品名}-{投放日期MMDD}-{时间HHMMSS}
全部       组名 = {品库该行品名}-{投放日期MMDD}-{时间HHMMSS}
```

后缀**一律加，不是撞名才加**。投放时间每天不同，天然唯一；一律加还能让同一批表里的命名保持
一致，而「撞了才加」会出现同一张表里有的带后缀有的不带，事后没法一眼看出哪些是新开的。

组名也必须带后缀：对「可扩」的品，品库品名往往**正好就是**账户里已有的那个组名。

系列名的基名取**品库该品第一行的品名**，多组的品其余行系列名列留空（见 5.1）。
`build_expand_sheet` 也能生成，但它要 `sourceAdGroupIds`，**「新建」类没有源组用不了**；
混用两套命名会让同一张表里的名字不一致，所以整表统一按上面的规则自己拼。

表有 7 列：`推广系列名称 / 广告组名称 / 视频代码 / 产品 URL / 年龄 / 性别 / 编码`

- `产品 URL`、`年龄`、`性别` 从**品库**那一行读，不要从账户猜
- `编码`列**只用于对账和反查，绝不参与命名**。名字一律以表里写死的为准

**品库列为空怎么办**（`年龄` 和 `url` 经常是空的，投手有意留空）：

| 列 | 品库为空时 |
|---|---|
| `年龄` | 沿用这个品**上次导入时填的值**（`build_expand_sheet` 已有此行为）；再没有就留空 |
| `url` | 同上。仍然取不到就**留空并在 incomplete 里点名**，让投手补——**绝不编一个** |
| `性别` | 取不到按「不限」 |

**url 只写到域名/商品页就够了**，不要手拼归因参数：创建时软件会自动补上
`utm_source/utm_medium/utm_id/utm_campaign`（`appendTrackingParams`，幂等）。表里手拼一遍
不会出错但没必要，而且拼错了反而会让软件跳过自动补。

账户快照里的广告组**没有落地页和定向**（只有名字、状态、预算、指标），所以「从账户读 url」这条
路根本不存在，别去试。这些值只存在于历史导入记录里。

### 5.1 一个品素材超 50 条：拆成多个组

一个组最多放 50 个素材，超了就拆。**没有上限两组这回事**——实测 `DM003217` 占 5 行
（50+50+50+50+37 = 237 个素材）。永远按源代码库的实际行数来，不要写死。

三边各记各的、**没有一处需要重复维护**：

| | 怎么表示 | 谁维护 |
|---|---|---|
| **源代码库** | 同一个编码**占 N 行**，各行编码字面完全一样 | 自动更新 |
| **品库** | N 行：`DM002451` / `DM002451-1` / `-2` … | 投手手工 |
| **导入表** | 系列名**只写第一行**，其余行留空 | 你生成 |

**⚠️ 不要让投手去源代码库加 `-1`。** 它自动更新，手改会被静默覆盖；而且分批信息它本来就有。

**怎么把品库的行配到源代码库的行**

**按行序一一对应**：品库第 1 行 ↔ 源库第 1 行，第 2 行 ↔ 第 2 行，以此类推。

只有两批时可以拿「满 50 = 第一批」当判据，但**三批以上这招就废了**——`DM003217` 前四行
都是满 50，只有末行是余数（37），靠数量根本分不出第 1/2/3/4 批。行序是唯一可用的判据。

飞书返回顺序实测是稳的（连拉两次 838 行完全一致）。**用完要自检**：最后一批之外的每一批
都应当是满 50，末批是余数。不符合这个形状就**不要猜，报给投手**。

**后缀规则**：第一个组**不带后缀**，第二个才是 `-1`。这个不对称容易读反，配错就是几个组
的素材对调。剥后缀取品编码时用 `^(.+?)-(\d+)$`——源代码库的编码前缀是
DM/FY/JM/SHDM/YK/HW/SJ/DFY，全是字母+数字，**没有一个自带横杠**，不会误伤。

**品库行数与源库行数要对账**，两个方向都可能出问题：

- 品库少写（`DM001273` 品库 1 行 vs 源库 50+7 两批）→ 那 7 个素材永远投不出去
- 品库多写 → 多出来的组拿不到素材，视频代码列会是空的

对不上就报给投手，让他自己改品库。这是出表时唯一能提前抓到「素材静默丢失」的地方。

**判定按品编码判一次，两行共享结果**

剥掉 `-N` 得到品编码，同一个品编码的所有行归**同一条系列**：

- 判**可扩** → 两个组都在原系列里扩，系列名照抄，第二行留空
- 判**需重扩** → 两个组一起搬到新系列，新系列名同样只写第一行

绝不能分开判。它们物理上在同一条系列下，而判定依据（累计 CPA、有没有在投组）全是
**系列级**的——分开判会算出「CZX 可扩、CZX4 重扩」这种执行不了的结果。

**⚠️ 定向绝不能读第二行**

第二行的 `年齡` / `性別` 经常是空的（实测 DM001019 / DM002393 / DM002392 的第二行都空，
只有 DM002451 两行都填）。规则是：**从品库那一行读，品库空了取源代码库的第一行**，
取到第二行的空值会让第二个组变成不限定向，白白多花一半钱。

**一条自检**：源代码库的行数就是「该建几个组」。出表时对一下——

```
品库里 DM002451 系列的行数  ==  源代码库里 DM002451 的行数
```

对不上就报给投手。这能提前抓到「品库少写一行 → 19 个素材没投出去」，比事后翻数据强。

### 6. 查重名（必做，不是可选）

```
check_names(accountId, campaignNames=[...], adGroupNames=[...])
```

因为系列名就是控制流，撞名的后果不是被拒，是**扩错地方**：
- 新系列名意外撞上某条不相干的系列 → 组悄悄并进了错误的系列
- 账户里本来就有两条同名系列 → 导入时指向哪条是歧义的

撞了就换名，不要留给投手发现。

### 7. 补视频代码

从源代码库按编码取 `代码合集`：

```bash
python .claude/skills/tk-expand-sheet/scripts/feishu_read.py --table tbl4IgEwXruyusk1 \
  --fields 编码 爆款产品 代码合集
```

`代码合集` 是用 `;` 拼接的素材 ID，直接填进「视频代码」列（导入表本来就支持一行多代码 = 组内多条广告）。

⚠️ **源代码库的「编码」可能是合并编码**：同一个品的两个货号写成一行、用 `/` 分隔，例如
`FY13124/DM002406`（VC素顏霜/五重維c素顏霜）、`DM003141/FY13345`。按字面相等去匹配会**整个
漏掉这些品**，表现为「源代码库里没有这个编码」——但它明明在库里，只是挂在一个复合键上。

建索引时按 `/` 拆开，每个子编码都指向同一行。实测这一个改动就让两个品从「拿不到代码」变成
拿得到。**别按品名去反查兜底**：库里有 13 个品名都带「素顏霜」，猜错的代价比漏掉大。

⚠️ **一个编码在源代码库里可能占多行**（实测 830 行 / 825 个唯一编码）。这时**不要把多行的
代码合集合并成一串**——一个组最多放 50 个素材，合并出来的 69 个装不下，多的会被丢掉或直接报错。

正确做法是**按行分配给对应的组**：满 50 的那行给品库的 `DM002451`，余数那行给 `DM002451-1`。
完整判据见 [5.1 一个品素材超 50 条](#51-一个品素材超-50-条拆成两个组)。

只取第一行同样是错的——那样余数那批素材（19 / 9 / 12 / 2 个）永远投不出去，
而且从结果上看不出来，因为第一个组看着是满的。

### 8. 对账并交付

报四个数：

```
可扩 N1 + 重扩 N2 + 新建 N3 = N（品库去重后的品数）   ← 必须相等
导入表行数 = 品库去重后的行数                          ← 必须相等
待清理：账户里在跑、但品库里没有的品                    ← 单独列出，不动手删
```

- **行数和品数是两个数，都要对。** 品库按广告组单元编制，素材超 50 的品会占多行
  （`DM002451` + `DM002451-1`），在导入表里也是多行。判定按**品**做（同一品的多行共享一个
  判定），行数则要跟品库去重后的行数逐一对上
- 等式不成立说明判定有 bug（漏了或重了），**不要交付，先查**
- **交付前把生成的表读回来核一遍**，别只信生成时的日志。至少查五项：组名撞不撞账户里已有的、
  表内组名有没有自撞、带系列名的行数是否等于品数、「可扩」的系列名是否真的存在于账户
  （不存在就会变成新开一条）、多组品的续行是否紧跟首行且编码同根
- 「待清理」只出清单给投手过目，不要自己删
- 差出来的品要能**点名是哪几个编码**，不能只报数量

产出 `.xlsx` 路径交给投手，他会手动导入，或者让你用 MCP 扩组。

## 不要做的事

- **不要替投手决定 `confirm=true`。** `expand_ad_groups` 和 `copy_campaign` 会真实花钱，默认只做
  预演（dryRun）。必须投手明确说执行，才带 confirm 再调一次
- **不要拿编码去拼系列名或组名。** 拼装差一个字符（分隔符、日期、大小写），本该并进原系列的组
  就会另开一条，而表里的编码列看着还是对的，从结果上查不出来
- **不要改飞书表。** 应用**有**读写权限（建品库表时开的），所以这条从「做不到」变成了「不该做」
  ——品库是投手一行行手工维护的选品结果，写进去一次就可能盖掉他的判断，飞书那边也没有版本回退
  给你兜底
- **不要因为账户里某个品命名不规范就跳过它。** 落「需重扩」，重开一条规范的
- **别的会话可能在同一个仓库里干活。** 撞见自己没写过的改动或临时文件（`.xxx-before.*` 这类
  工作快照）就绕开，别删别改；先 `git diff --stat` 比对范围确认与自己无关。测试要用
  `pnpm -r --no-bail test`，否则别人的失败会中断递归、掩盖掉你自己那个包的失败

## 已知坑

- **读飞书字段值一律用 `fetch_flat()`，不要用 `fetch_records()`。** 后者返回飞书原样的记录，
  文本列长这样：`[{"text":"DM002451","type":"text"}]`。直接 `str()` 拿去比较永远不相等，
  **不报错**，只表现为「一条都匹配不上」。实测代价：编码命中率 0/431 vs 339/431
- **双科两个账户的品不在源代码库里。** 般朵-TT-001（46 个品）和全娘-TT-002（14 个品）的
  编码命中 0、品名命中也 0——不是命名不规范，是这些品压根没进过「爆款整理」表。给这两个账户
  出表时拿不到代码合集，视频代码只能留空让投手补
- **飞书中文字段名必须走 POST body，不能走 GET 查询串。** 在 Git Bash 里 GET + 中文参数会被编码
  坏掉，报 `FieldNameNotFound`，看起来像字段不存在。用 curl 同样踩。脚本已经处理了
- **Windows 上跑 Python 记得 `export PYTHONIOENCODING=utf-8`**，否则中文输出变乱码，报错信息看不懂
- **飞书分页要走到底**。品库和源代码库都是几百上千行，只取第一页会静默少数据，表现为「这个品在
  品库里没有」——最难查的一类错。脚本已经处理了
- **账户里的系列命名不统一**：有的带编码（`FY13388多功能強力廚房剪刀低价测试`），有的不带
  （`透氣彈力休閒褲-0902-060000`）。这是历史命名退化，别指望所有系列名都能解析出编码
- **账户快照拿不全时别硬扛 MCP 的输出截断。** `list_campaigns` 按累计花费降序截断（675 条系列
  只列前 60 条），而判定需要每条系列的名字去匹配编码。全量数据直接查生产库更省事：
  `provider_entities`（`payload_json` 里有 `campaign_name` / `campaign_primary_status` /
  `campaign_create_time`，广告组那边有 `campaign_id` / `ad_name` / `ad_primary_status`）
  加 `entity_metric_snapshots`（`metrics_json` 里是 `spend` / `conversions`，累计口径，
  按 `captured_at` 取最新一条）。库在「文档\TK Ads Automation\data\tk-automation.db」，
  **只读打开**
- **素材超 50 拆多行的品**（2026-09-08 实测 838 行源代码库）：DM003217 占 5 行，
  DM002451 / DM001019 / DM001870 / DM002393 / DM002392 / DM003218 / DM001273 各占 2 行。
  数量少但必须处理对——配错就是几个组的素材对调，
  而且从结果上看不出来。详见「5.1 一个品素材超 50 条」
- **单次导入上限：5000 条广告 且 500 行**（1.4.109 起）。两个独立闸门，一行 50 个代码时
  100 行就顶满 5000 条。生成表时留意别一次出太多，超了导入页会直接拦下
