# TK Ads Automation

面向 TikTok 广告优化师的本地优先自动化管理工具。

## Windows 桌面版 1.4.35

安装包：`apps/desktop/release/TK-Ads-Automation-Setup-1.4.35.exe`

- 适用于 Windows x64，双击安装后从桌面或开始菜单启动。
- 不依赖自建服务器；界面、本地 API、SQLite 和 DPAPI 凭据库均在本机运行。
- 用户数据保存在“文档\TK Ads Automation\data”，与安装目录分离。
- 首次安装并打开客户端时，会启动名为“tk自动化后台程序”的无窗口后台调度器，并默认写入当前用户的开机自启。
- 关闭客户端窗口会最小化到系统托盘并显示提醒；托盘菜单可完全退出客户端，后台程序继续运行。系统总开关关闭时会同时停止后台程序和开机自启。
- 后续升级先关闭程序，再直接运行更高版本安装包；不要先卸载旧版本。
- 固定 App ID `com.tkads.automation`，新版安装包覆盖程序文件并保留用户数据。
- 当前安装包未配置商业代码签名证书，Windows 可能显示未知发布者提示。

升级到 1.4.101 后会出现的变化：

- **AI 助手可以直接接进来了（MCP）。** 上新素材要走批量创建表，而表里的系列名和广告组名得手工填——账户里同一个品有一堆名字相近的对象（原始的 `八寶茶`、复制出来的 `八寶茶-0805-143052`、在那条上又扩的 `八寶茶-0812-091530-1`），肉眼分不清哪条是当前该用的；填重了 TikTok 直接拒，填错了新素材就上到废组上。现在 Codex 和 Claude 桌面端可以直接读快照、判谱系、生成一张只差视频代码的导入表。安装目录的 `resources/mcp/mcp-server.cjs` 由已装的 Electron 以纯 Node 模式运行，不需要另外装 Node。
- **谱系判定分「确证」和「推断」两级，不合成一个看起来对的答案。** 确证来自 `campaign_copy_tasks` / `ad_group_expand_tasks` 里记下的「源 → 产物」；推断只说明名字能被自动后缀剥离认出来，但任务记录已过 30 天清理期、源头无从查证。同时列出账户内的同名系列与同名广告组——那是撞名被拒的直接来源。品名归并只用确定性的后缀剥离，不做模糊匹配：靠名字猜品会把 `DM003142八寶人蔘枸杞茶` / `八寶人蔘枸杞茶` / `八寶茶` 拆成三个品，猜错的代价比不猜大。
- **生成的导入表就是导入页真吃得下的表。** 系列名与广告组名复用一键扩组的同一套命名函数（`{清洗后源名}-{MMDD}-{HHMMSS}-{序号}`），并避开账户内已占用的名称——包括刚建好、还没被同步捕获但任务记录里已经写下的那些。产品 URL 与定向沿用这个品上次填的值，取不到就留空并点名哪几行要补，不编一个填进去。生成表不创建任何对象、也不占用名称。
- **助手做的扩组和系列复制默认只做预演。** 先返回「要建什么、叫什么名、多少预算、有没有冲突」，用户明确同意后才真正下单。走的是与界面完全相同的那条路：幂等闸门、冲突预检、写熔断、「结果未知禁止自动重试」一条不放松，操作记录里的执行者记为 `mcp-agent`。该身份角色为操作员，改不了系统设置也管不了本机账户，在「用户管理」里可以随时停用。
- 本地 API 的会话令牌现在也接受 `Authorization: Bearer`。认的是同一张会话表，权限判定与 CSRF 校验完全不变——只是 MCP 这个纯 HTTP 客户端没有浏览器的 Cookie 罐。接入信息写在 `%APPDATA%\TK Ads Automation\mcp-endpoint.json`，里面是一张真实令牌，不要外发。

升级到 1.4.34 后会出现的变化：

- **过夜关停不再被规则当场抵消。** 2026-08-07 晚上：23:45 过夜排期关掉 4 个组，23:50–23:52 启停规则又把其中几个开了回来，零点排期再开一次，00:07 规则又关掉——「翻譯機_新」一晚上被开关四次。根因是 `enrollNightlyAdGroups` 用 23:45 这个窗口触发关闭，而自动派发那一侧从来没有任何时间门禁。现在本地 23:45 至零点内规则不再自动开启广告组，需要投放的由零点过夜排期统一打开；关闭方向不受限制，它和窗口同向。
- **零点至凌晨 3 点不再用规则调整过夜组。** 过夜组在零点刚被排期开回来，当日数据从零开始，任何基于消耗/转化的规则都会立刻判它「零转化消耗过高」而关掉。这三小时留给它们攒数据。**只保护过夜组**：同一时段里其它广告组（刚创建的、本来就在跑的）不受影响，规则照常判定。两段窗口的判据与 `enrollNightlyAdGroups` 共用一个函数，避免同一件事在两处各写各的。
- 以上只约束规则引擎；过夜排期本身和人工启停不受影响。
- **跨账户复制可以直接点创建。** 最常见的阻断项是「目标账户没授权到某条原帖」，而没授权的本来就复制不过去，把人挡在创建之前、逼着反复重新生成预览没有意义。现在原帖检查与预览过期都不再阻断，只有「一条可创建的条目都没有」时才拒绝，并把具体原因带出来。界面同步放开：有阻断项时不再隐藏源组列表与逐账户表格，阻断项改述为「会在执行时跳过，其余照常创建」。`inputHash` 与预设快照完整性校验保留——它们防的是「预览内容和你要创建的不是一回事」，是另一码事。
- **一条失败不再拖垮整组。** 系列批次的逐条预检（原帖证据、attemptId、复制模式的 templateCampaignId）此前直接抛出并落在批次级处理里，十条里有一条不合格，另外九条明明没问题也一起判失败。现在坏的那条单独标失败并剔除，其余照常创建；全部都不过才整批失败，此时不再调用 Provider。
- **操作历史只保留 30 天。** 客户端 24 小时跑着、每 30 秒一轮，上线 25 天就攒了 3.6 万条审计、1.4 万轮轮询、1.2 万次自动化运行。现在超期的操作记录、决策、运行、同步、审计、通知与轮询记录会被清理，每 6 小时执行一次。**还没收口的写任务（pending / running）不管多老都保留**，它们是待办不是历史；`entity_metric_snapshots` 也不动，它是 90 天指标日历的数据源。

升级到 1.4.33 后会出现的变化：

- **从零创建的广告组终于能发布出去。** 2026-08-08 凌晨从零创建的 10 条全部死在发布，TikTok 回 `uaa_campaign_automation_inconsistent_error`（广告组层 `ad_error_items`），而草稿本身是好的——手动打开广告组页面、等页面加载完再点发布就能成功。抓包定位到缺的是 `snap/save_by_sketch`：TikTok 的 `sketch` 是持久草稿，`snap` 是一次编辑会话的工作副本，页面加载时会按 `campaign_sketch_id` 把整棵树（系列/广告组/创意）重铸一套新 snap，之后的检查与发布全部引用新 snap。我们一直拿建草稿那一刻的旧 snap 去发布，系列层的 automation 字段在那之后才被归一化，元组因此对不上。现在新建系列在发布前重铸 snap，`sketch_publish_source` 也对齐真机的 `2`。
- 重铸的映射表缺任何一项就停在发布之前，不拿旧 snap 硬发——旧 snap 必然被拒，早停才不会产生正式对象。只作用于「从零创建」；复制/扩组自带回读再保存，生产上一直正常，未作改动。
- **同名系列自动复用：命中就只建广告组，不再新建系列。** 此前只在同一批次内按系列名复用，跨批次遇到线上已存在的同名系列仍会去新建，被 TikTok 判重名拒绝。现在派发前查一次账户快照，命中同名系列就把广告组加进去（`is_partial_publish`）。注意复用意味着新广告组继承那个系列的设置（营销目标、预算方式、Smart+ 与否）；预设与既有系列不一致时以既有系列为准。
- 账户内存在多个同名系列时明确报错而不是随便挑一个：发布后的终态核验按系列名精确匹配，多个同名会让核验无从判定哪个是本次创建的。快照滞后（刚建好、还没被同步捕获）时查不到会照旧新建，与升级前行为一致。

升级到 1.4.32 后会出现的变化：

- **自动申诉从 0% 成功变为可用。** 申诉报文是手写的，从未对过真机抓包，三处不一致叠加导致 TikTok 在解 JSON 时就拒绝：`creative_id` 应是**数字**字面量却发了字符串（服务端回 `json: cannot unmarshal string into ... int64`）；`ad_id` 装的是**广告组** ID 而不是广告自己，此前两个位置都填了广告 ID；`aadvid` / `advertiser_id` / `adv_entry` 三个必填字段根本没发。查询串上的 `req_src=bidding` 一并补上。现已按真机样本逐字段写成测试钉死——此前那条测试的名字就叫「without an account appeal import」，把手写报文断言回它自己，等于没测。
- 广告 ID 逐位原样发出，不经过 `Number()`。TikTok 的 ID 可以长到 19 位、超过 2^53，先转数字再序列化会静默改写末几位，申诉就打到别的广告上去了。取不到广告组 ID 时明确报错并且不发请求。
- **申诉失败不再无从诊断。** TikTok 会在 `content-type` 仍写着 json 的情况下回一段纯文本错误，此时 `response.json()` 抛的是 JS 自己的 SyntaxError，只带十来个字符预览。2026-08-06 三条自动申诉全败，库里只留下 `Unexpected token 'j', "json: cann"...`，到底哪个字段不对被丢掉了。现在响应体脱敏后进错误消息，这条对所有 Cookie 请求生效，不只申诉。
- **结果未知不再永久拉黑一条广告。**「结果未知的不可逆操作绝不自动重试」对删除和启停成立，对申诉不成立：重复提交一次申诉不花钱、不改投放、不删对象，代价远低于永远不再申诉。上述三条被判未知的广告因此被永久踢出候选池，而当天值得申诉的总共只有四条。改为与明确失败一样计入次数、由重试上限兜底；申诉成功过的、以及还在排队或执行中的仍然不重复提交。升级后这三条广告会自动回到候选池。

升级到 1.4.31 后会出现的变化：

- **复制和一键扩组建出来的广告不再是关的。** 复制是让 TikTok 按源对象克隆，广告的开关状态一并被克隆过来：源广告组里的广告是关的，新组里的广告也是关的，于是组开着、广告关着，整组投不出去。发布载荷里只有 `is_status_disabled` 一个开关且只作用于广告组层，创意快照里没有状态字段，所以只能在拿到本次新建的广告 ID 之后再显式开一次。
- 开不开跟着**广告组的发布状态**走：组以 enabled 发布就开，组以 disabled 发布就全部保持关闭。原生定时投放的组本来就是以 enabled 发布的，同样要开——拦住投放的是 TikTok 按广告组排期判定的 `ad_time_no_reach`，不是广告自己的开关。生产快照里创建即为关闭的 6 条广告有 5 条属于定时批次，把定时批次排除在外等于这个修复基本不生效。
- 安全边界：只处理本次发布结果里返回的广告 ID，不碰任何存量对象；开启失败不推翻整次创建（广告组已经建好，判成失败会诱发重复创建），失败明细汇总进返回消息；账户没有导入广告层开关 cURL 时照常返回成功，并说明广告保持了克隆来的状态。
- 按当前生产快照回放：由复制/扩组建出来的 129 条广告里，98 条本来就是开的（这次改动只是重复开一次，状态不变），6 条本来是关的会被真正打开，其余 25 条后来被自动启停规则动过、无法归因。

升级到 1.4.30 后会出现的变化：

- **广告层启停从 0% 成功变为可用。** 此前广告层的开关请求是从广告组 cURL 派生的，派生时把 `creative_list` 原样复制了一份到 `aco_creative_list`。对照真实抓包，这个列表应当是空数组——它装的是 ACO 创意，和普通广告是两类对象。把普通广告 ID 塞进去，TikTok 一律以 `code 4` 「Smart+ 推广系列不支持特定界面」拒绝，生产环境广告层写入 67 次全败、零成功。
- 除这一个字段外，派生结果与真实广告层请求逐字段一致（路径 `/ad/` → `/creative/`、overture 版本号 v3 → v2、`ad_list` → `creative_list`、`operation` / `ad_channel` / `risk_info` 原样沿用）。现已用两条真实抓包样本写成测试钉死。
- 升级前存下的模板不必重新导入：执行时会强制把 `aco_creative_list` 置空，存量账户装上新版即自愈。

升级到 1.4.29 后会出现的变化：

- **自动申诉开始有候选可跑。** 此前判据读的是单数字段 `creative_status` 且只认 `creative_offline_audit`，而 TikTok 用 `creative_status_list` / `ad_status_list` 表达「一个对象同时处于多个状态」，单数字段只是列表第一项。生产快照里 35 条带审核问题的广告有 29 条长成 `["ad_disable","creative_review_partially_approved"]`，单数字段读出来是 `ad_disable`——两个缺陷叠加，命中数恒为 0，申诉从未排过一次队。现在解析列表，并同时认「完全审核下线」与「部分版位未过审」（界面上的「未全部投放 · 审核问题」）。
- 已经关停的广告不再申诉：恢复过审也不会投放，真要重开时再申诉更合理。按当前快照，35 条候选里 29 条属于关停状态，实际会提交的是仍在投放的 6 条。
- 申诉的去重口径未变：一条广告成功或结果未知后不再重复提交，明确失败最多重试到配置的上限。

升级到 1.4.28 后会出现的变化：

- **自动删除广告组终于能真正下单。** 2026-08-06 早上删除执行器第一次按时启动，四个账户全部领取任务，但 66 个删除请求全部在发出前失败：删除请求是把广告组关闭 cURL 里的开关字段改写成 delete 派生出来的，而这段代码写死了 `operation_status`，TikTok 当前接口用的字段名是 `operation`。现在改用与 cURL 导入完全相同的判据（`status` / `operation` / `operation_status` / `opt_status`），并沿用原值的大小写。
- 删除能力的上报口径收紧：模板里没有可改写的开关字段时不再宣称"删除可用"。此前只检查模板是否存在，于是界面显示可用、执行器领走当天任务，然后整批失败。
- 停在 validation 阶段（请求从未构造成功、TikTok 侧什么都没发生）的删除失败不再永久占住该广告组。此前只要有任何一条 delete 记录就永远跳过，导致上述 66 个广告组在根因修复后仍然不会被重试。真正发出过的删除（`phase=dispatch` 及以后）仍然永久占坑——结果未知的不可逆操作绝不自动重试，这条没有放松。

升级到 1.4.27 后会出现的变化：

- 同步质量改为**按层级**判定，一层拉不到不再连坐其余层。此前只要广告层的派生请求超时，整轮同步就被判 partial，账户显示「读取：未就绪」，删除和自动复制也被整轮跳过——尽管它们只用广告组和系列的数据，而这两层往往几秒就取全了。实测一个账户约 50% 的轮次会因广告层超时而被连坐。
- 与之配套：partial 同步现在也会**刷新本轮取全的层级**，只有失败的那一层保持上一轮的数据。此前 partial 一个实体都不写，广告组快照会原地不动。这是让按层级判定成立的前提——否则执行器会拿旧快照当新数据，新鲜度判据会失真。契约漂移（invalid）仍然一层都不刷新：那是全局问题。
- 升级前写下的 partial 记录没有层级信息，继续按旧的「整轮不可用」处理，不会被追认为可删除的依据。
- 同步警告如实说明是否重试过。超时走的是不重试分支，此前固定写「已重试 1 次」是错的。

升级到 1.4.26 后会出现的变化：

- 只读列表请求的超时预算从 15 秒放宽到 45 秒。1.4.25 上线后拿到了失败原因，实测广告层级失败的真正原因是**客户端自己的 15 秒超时到点**（`The operation was aborted due to timeout`），不是此前推测的 TikTok 限流。失败账户与广告条数完全对应：100 条的稳定卡在这个边界，75 条的偶尔卡，62 条和 2 条的从不卡。只放宽只读列表这一条路径；创建、启停、删除等写请求继续用 15 秒，它们的超时语义是「结果未知」，拖长只会扩大不确定窗口。
- 超时不再重试。1.4.25 加的「失败重试一次」对超时是纯浪费：一个已经等满预算还没回话的请求，再等一轮也不会回话，只会把整轮轮询从 8 秒拖到 90 秒以上（实测中位耗时从 7.2 秒涨到 14.4 秒，最长 46.8 秒）。重试保留给 5xx、连接重置这类真正的抖动。

升级到 1.4.25 后会出现的变化：

- 只读列表请求失败后会自动重试一次。此前广告层级的派生请求一失败就放弃，整轮同步被判为 partial（`ad` 计为 0 条），账户在界面上显示「读取：未就绪 / 待完善」，直到下一轮同步才恢复。这不只是显示问题：删除和自动复制都要求最近一次同步为 healthy，partial 期间会被连带跳过。（当时推测该类失败是 TikTok 限流，**这个判断是错的**，真实原因见 1.4.26 条目。）
- 派生请求失败的真正原因会写进同步警告。此前只留一句「自动补全请求失败」，39 条历史失败记录里查不出是限流、超时还是会话失效。现在会带上 HTTP 状态码或底层网络错误码——正是这一条在上线后立刻暴露了上一条的错误前提。
- 「可用能力」一栏现在会显示"删除"。此前该栏的标签表漏了 `delete-ad-groups`，而没有标签的能力会被整条过滤掉，导致已授权删除的账户看起来像缺了这项能力。仅显示口径变化，不影响任何权限判定。

升级到 1.4.24 后会出现的变化：

- 自动删除广告组开始真正执行。此前它从未跑过一次：执行器被放在「轮询到期」过滤之后的循环里，只有恰好在计划时刻到期的那一轮才有机会评估，生产环境 19 天里只命中过 7 次，平均两三天才有一次机会，且每次还要再过一道「同步年龄 ≤ 5 分钟」的门。现在它和自动申诉一样每 30 秒对全部账户评估一次。
- 触发窗口从「计划时刻整点那一分钟」放宽到整个计划小时。一个账户真删起来几十个组要跑一分钟以上，锁死第 0 分钟会让排在后面的账户永远轮不上。每账户每个本地日仍然只执行一次。
- 计划小时改为读取删除设置里的 `scheduleHour`，不再硬编码为 6（当前配置仍是 6，界面上暂无修改入口）。
- 删除本身的安全护栏一律未动：只删软件明确关闭且最新同步仍为关闭的组、24 小时保护期、转化/加购/CPA 阈值、每系列至少保留一组、结果未知禁止自动重试。

升级到 1.4.23 后会出现的变化：

- 广告层级恢复同步。此前每轮同步广告数恒为 0：两段式导入只捕获了广告组列表 cURL，系统派生最终广告列表请求时只替换了路径、没有替换统计维度，TikTok 因此按广告组维度作答，返回的每一行都是 `creative_id` 为 0 的占位行而被整行丢弃。现在会同时改写维度，四个账户实测从 0 条恢复到 86/53/2/75 条。受此影响的还有两处：自动申诉从未真正执行过（它只处理广告层级对象，而候选集一直是空的），以及广告层级的规则判定同样一直没有对象可跑——升级后这两项都会开始工作。
- 创建结果核验用的是同一条派生请求，此前也读不到广告，这是「创建终态不完整」的成因之一。
- 系列复制、扩组和自动复制的命名统一为「清洗后源名-投放日期-时间」（例如 `奢台記錄儀_新-0805-143052`），精确到秒。投放时刻取排期时间，立即投放取执行时间，按账户时区。名称天然唯一后不再依赖账户快照推算序号，1.4.22 加的发布前强制刷新随之移除。
- 扩组此前的序号固定从 1 重新编号且完全不查账户已有名称，同一天对同一个源第二次扩组必然撞名被 TikTok 拒绝；现在靠时间戳区分批次。
- 自动复制改为同一来源只复制一次（此前是每天一次），并且复制出来的广告组在整个账户范围内永远不再作为复制来源——此前的排除只在同一个系列内生效，且会放过标记为失败但可能已部分创建的任务。
- 自动复制的命名模板配置项移除，命名不再可自定义。旧配置里的模板值会被自动忽略，不需要手工迁移。
- 注意：自动复制的任务标识随本次改动变化，历史「已复制过」的记录匹配不上新标识，升级后第一轮可能对存量来源各复制一次。
- 系列复制遇到网络中断等传输层错误时，只要能确认写请求根本没发出去（连接被拒绝、域名解析失败等），会自动重试，不再一失败就整条任务卡死；任务级最多自动重试 3 次。
- 若某个系列复制任务在写请求发出后失去了确认结果的能力（网络中断、超时等），系统无法自证是否安全重试，会照常停止自动重试并标记为「结果未知」——但现在系列复制面板会直接列出这些任务，人工在 TikTok 后台核实真实状态后可以点击重置，允许系统重新领取执行；此前唯一的处理方式是联系开发者手工改数据库。
- 无此类卡死任务时面板不会显示新增区块，不影响原有使用流程。

当前版本实现本地检测、决策与受保护的双 Provider 状态管理：

- 用户管理中的账户自动化总开关
- 用户管理内的账户编辑、接入与连接状态轮询
- 九条全局规则配置（数值可修改、单条可启停）
- Cookie / Official API 双 Provider 边界
- Windows DPAPI 加密凭据库
- 首次启动开发者账户、本机登录、角色权限、HttpOnly 会话与 CSRF 保护
- 左上角全局自动化开关：关闭后暂停自动检测、定时规则、通知和自动启停；广告创建和人工启停不受影响
- 两段 cURL 快速导入（两个输入框、一个导入按钮、五个必要字段状态）
- 单条状态 cURL 自动生成三个层级的开启、关闭模板
- 多广告账户独立凭据与全账户共用自动化规则
- 系列、广告组和广告分页检测与指标标准化
- 账户启用后默认自动执行；检测预览始终只读
- Cookie 真实状态 cURL 模板与官方状态更新 API
- 忽略名单、手动启停、申诉队列和操作记录
- 广告组单次定时和每日过夜开关
- 90 天指标快照、日历范围与检测批次柱线组合图
- 邮箱、企业微信和飞书轮询结果通知
- 自动申诉、复制和删除的全局配置骨架（真实执行器待 Provider 请求）
- 系列预算与广告组预算两种模式，创建广告页面一键切换（四个创建功能共用）
- 系列复制：把一个推广系列复制成 N 个新系列，并指定每个新系列放 M 个广告组
- Excel/CSV 批量创建配置：账户统一选择、空白继承、逐行校验和多账户分发
- 相同广告多账户投放计划（真实创建执行器待 Provider 请求）
- 本地 SQLite 持久化、调度器和审计记录
- Web 置顶操作手册与自动生成 Markdown 手册

程序不会自动读取浏览器 Cookie。Cookie 用户通常只需在第 1 步导入一条
`/adgroup/list/?` cURL，并在第 2 步导入一条 `/ad/update_status/?` cURL，系统会扩展
三个层级的双向模板。自动化只处理当前时间向前 48 小时内创建的推广系列；
九条规则由全部账户共用，推广系列默认不应用，广告组和广告默认应用。账户总开关和
单条规则开关开启后即按轮询计划自动执行，不再设置额外执行模式或能力开关。

## 架构

```text
apps/web        可复用于 Web 与桌面壳的管理界面
apps/api        仅监听本机的 API 服务
apps/mcp        给 AI 助手用的 stdio MCP 服务（只调本机 API，不直接开库）
packages/core   领域模型、校验和配置规则
packages/providers  Cookie / Official API 适配接口
packages/credentials Windows DPAPI 凭据库
packages/manual  Web 与 Markdown 共用的操作手册数据
packages/storage    SQLite 数据层
```

业务代码只依赖统一的 `AdsProvider` 接口。以后可以按账号选择 `cookie` 或
`official-api`，无需修改账户总开关和规则引擎。

## 安全边界

- API 默认只监听 `127.0.0.1`。
- 所有业务 API 默认要求登录；写操作同时校验 CSRF 和服务端角色权限。
- 密码使用 scrypt 随机盐哈希保存，会话只在 SQLite 保存不可逆令牌哈希。
- 不在数据库中保存明文 Cookie 或 Token。
- SQLite 的 `credentialRef` 只保存 Windows DPAPI 凭据文件的随机引用。
- cURL 中的 Cookie、CSRF、msToken、签名、完整 URL 和 Payload 均进入 DPAPI
  加密保险库，不以明文写入 SQLite。
- Cookie 请求只允许 TikTok 官方 HTTPS 域名，并禁止自动跟随重定向。
- 外部请求优先使用 HTTPS_PROXY/HTTP_PROXY；Windows 下未设置环境变量时自动继承当前系统代理。
- Provider 未通过连接检测时禁止检测和写入。
- 忽略对象、冷却期对象和超过单轮上限的对象不会执行。
- 连续三次写入失败会熔断本轮；启用规则命中时，手动关闭的对象也可能被重新开启。
- 所有配置变更写入审计日志。
